# Session record — 2026-11-17

Everything below was measured on the device or parsed from its own firmware. Nothing here is
"should work"; each line has an observation behind it.

## 1. What still works

| Layer | State |
|---|---|
Boot chain | BootShim + 3 MiB UEFI FD + appended DTB boots to the UniXNU menu, every time |
FrameBuffer console | primary debugging tool; `DEBUG_ERROR` reaches the panel |
XNU build (CI) | `kernel.macho` 51.9 MB and `payload.img` 78.6 MB build green on a macOS runner |

Growing the FD to 4 MiB is **not** possible: it collides with our own `SEC Heap` at
`0x9FF00000` (`ValidateMemoryMap` reports the overlap and halts). The compressed FV still has
~2.4 MB of headroom, so driver additions fit inside 3 MiB as long as the *uncompressed* content
stays reasonable.

## 2. Storage: closed, and why

The controller is healthy — this is the part that took the longest to establish:

```
UIC_CMD_DME_GET completes on the first poll (after a working W1C clear of IS)
GCC 0x77010/14/18/1c/58/5c/90/ac/c0/8c000 all report bit31 = 0 (not gated), core_clk = 0x4221
UFS_PHY_BCR = 0 (not in reset), GDSCR low byte 0 (not collapsed)
live device tree: ufshc@1d84000 has NO iommus property -> not behind apps-smmu
```

The single failing step is the controller fetching a descriptor:

```
door bell with the transfer list STOPPED -> harmless
door bell with the list STARTED         -> hangs the device
```

Six buffer placements and UFSHCI 3.0 descriptor semantics (inline UTRD, word-based offsets, per
QEMU's model) made no difference. `QCOM_SCM_MP_RESTORE_SEC_CFG` is implemented in the TZ
(`IS_CALL_AVAIL` returns 1) yet refuses every device id 1..20 with `-2`.

**Vendor binaries are not a shortcut.** `Project-Aloha/UEFIFirmwareBackup/iqoo-pd1936` holds this
exact device's signed driver set (`UFSDxe.efi` 118 KB, plus the vendor's own `APRIORI.inc` and
`DXE.inc`). The real DEPEX for all 76 drivers was recovered from the FV inside `xbl.elf`
(`tools/fv_depex_dump.py`, output in `vendor/iqoo-pd1936/vendor-depex.txt`). With those DEPEX
expressions in place `UFSDxe` still binds nothing, and the infrastructure drivers
(`ScmDxeLA` first) hang: they are XBL userspace binaries that assume XBL's SMEM / shm-bridge /
TZ runtime.

Conclusion: the UFS master's access to HLOS memory is fenced by platform protection configured
before hand-off. A plain MMIO `READ(10)` needs no secure world; making its DMA legal does.

## 3. USB host: the controller works, VBUS does not

The argument that carried this: Android moves adb/MTP traffic through dwc3 every day, so its DMA
into HLOS memory is permitted. Measured:

```
GCTL[13:12] forced to 1 (host), read back capdir = 1
XHCI CAP = 0x01100020 -> caplen 0x20, HCIVERSION 0x0110 (XHCI 1.1)
PORTSC1: PP=1, PLS=5 (RxDetect)   <- a host port actively scanning for a device
XhciDxe, UsbBusDxe, UsbMassStorageDxe all bind
```

`CCS` stays 0 and disks stay dark: **VBUS is missing**. The device tree puts VBUS on SPMI
(`pm8150_gpios 9` = `usb2_vbus_boost`, and the PM8150B SMB5 charger's OTG output).

SPMI from the firmware:

```
read : works   (arbiter v5; APID map entry holds the PPID at bits[19:8];
                obsrvr + 0x10000*ee + 0x80*apid; cmd = (opc<<27)|((addr&0xFF)<<4)|bc)
write: dropped for every APID mapped to the GPIO9 page, every write opcode
```

That is the `apid_data[apid].write_ee != our ee` rule Linux enforces. **Software VBUS is closed**
by the same class of protection as UFS. An externally powered hub is the only way to finish the
USB test.

## 4. SCM surface: wide, but gated

`IS_CALL_AVAIL` sweep: **120 calls available**. Memory-protection service `0x0C` exposes 18,
including `RESTORE_SEC_CFG` (0x02), `MP_ASSIGN` (0x16), `CP_SMMU_APERTURE_ID` (0x1B) and the
shm-bridge trio (0x1C/0x1D/0x1E). `SVC_SMMU_PROGRAM` (0x15) exposes 0x02 and 0x03 — a
CAF-private service that sounds exactly like the right lever.

Zero-argument probes:

```
MP 0x03 IOMMU_SECURE_PTBL_SIZE   -> x0 = 0 (accepted), x1 = 0 (nothing to report)
MP 0x1B CP_SMMU_APERTURE_ID      -> -5
MP 0x16 MP_ASSIGN (1 arg)        -> -5
SMMU_PROGRAM 0x02 (1 arg)        -> +4   <- only call that answered with a positive value
SMMU_PROGRAM 0x03                -> -5
same calls with 2 args           -> -5
```

A 12-vector sweep of `SMMU_PROGRAM 0x02` (arg counts 0..6, SID candidates 0 and 0x300) is built as
`boot-smmuprog.img` and still needs to be run.  Until it produces a `x0 = 0`, the "legal SCM"
route has not produced a usable entry point.

## 8. SCM: surfaced mapped, verdict reached (2026-11-18)

The full `IS_CALL_AVAIL` survey returned **120 available calls**. The memory-protection service
`0x0C` alone exposes 18, and `SVC_SMMU_PROGRAM` (`0x15`) exposes two. That surface was then
attacked with argument sweeps:

```
SVC 0x15 cmd 0x02 (SMMU_PROGRAM): 12 vectors, arg counts 0..6, SID candidates 0 / 0x300
                                  -> no vector returned x0 = 0
SVC 0x0C cmd 0x1B (CP_SMMU_APERTURE_ID), 0x16 (MP_ASSIGN), 0x0E, 0x0F, 0x23
                                  -> all rejected
SVC 0x0C cmd 0x03 (IOMMU_SECURE_PTBL_SIZE) -> x0 = 0, i.e. accepted, but it is a query
                                  ("how large must the secure page tables be"), it grants nothing
```

**Verdict: the legal SCM surface contains no call that lifts the memory fence.** The TZ routes
these commands but keeps execution authority; the one call it answers is read-only sizing
information.

### Lesson worth keeping: never hand-write `smc` in a DEBUG-heavy driver

An earlier build issued `smc #0` from inline asm and asserted immediately afterwards:

```
ASSERT [ScmTryDx] DebugLib.c(110): Format != ((void *) 0)
```

The TZ return path leaves registers in a state the asm had not declared, so the next `DEBUG`
call received a null format pointer. Any SMC from firmware must go through MdePkg's
`ArmSmcLib.ArmCallSmc()`, which saves and restores the full register set.

## 11. XBL reverse engineering: the SCM ABI, and why the MP calls are refused

`xbl.elf` was analysed in IDA (9.5, idat worker prestarted, UEFI plugin naming every function by
its module). Results:

### The transport, verified from disassembly

```
ScmDxe_QcomScmProtocol_Function7(proto, fnid, arginfo, args, res)   @0x100f2c18
    -> sub_100F29FC(fnid, arginfo, args, res, 0)                    @0x100f29fc
        -> sub_100F373C(fnid | 0x40000000, arginfo, args, &res)     @0x100f373c
```

`sub_100F373C` is the raw SMC wrapper:

```
   AND  W9, W1, #0xF          ; arginfo & 0xF must be <= 0xA
   LDP  X2, X3, [X19], #0x10  ; x2, x3 = args[0], args[1]
   LDP  X4, X5, [X19], #8     ; x4, x5 = args[2], args[3]
   SMC  #0                    ; x0 = fnid, x1 = arginfo
```

So the convention is plain SMCCC: **x0 = fnid, x1 = argument count in the low nibble, x2..x5 =
args[0..3]**, and the fnid carries `| 0x40000000` on top of whatever the caller passes.

### The fnid format, verified from call sites

```
sub_100E37E8 : 33555972 = 0x02000604  -> svc 0x06 cmd 0x04
sub_100E39A0 : 33556481 = 0x02000801  -> svc 0x08 cmd 0x01
sub_100E3A94 : 33555971 = 0x02000603  -> svc 0x06 cmd 0x03
sub_105E31B0 : 33559313 = 0x02001311  -> svc 0x13 cmd 0x11  (SVC_LMH)
```

i.e. `fnid = 0x02000000 | (svc << 8) | cmd`, owner = SIP (2). That is exactly what our own
firmware built, so **the shape of our calls was right** - the refusal was never a calling
convention mistake.

### What XBL does *not* do

39 functions reference `gQcomScmProtocol`; their call sites use the INFO (0x06), 0x08 and LMH
(0x13) services. **No call to SVC_MP (0x0C) and none to SVC_SMMU_PROGRAM (0x15) appears among
them.** The memory-protection service is therefore not configured from XBL's UEFI phase at all -
it is set up earlier, inside the secure boot flow, by the TZ itself.

### Consequence

The plan "recover the real argument structure of MP/SMMU_PROGRAM from XBL and call it correctly"
cannot succeed, because XBL never makes those calls: there is no reference parameter set to copy,
and the TZ rejects the service for any non-owner caller (`-5`). Combined with the earlier sweeps
(12 vectors for SMMU_PROGRAM 0x02, zero-argument probes of MP_ASSIGN / CP_SMMU_APERTURE_ID), the
legal-SCM route to lifting the UFS fence is closed with evidence rather than by assumption.

The USB host route is unaffected: dwc3 accepts host role, XHCI 1.1 comes up with PP=1/PLS=5, and
the mass-storage stack binds - only VBUS is missing, and that is a hardware (external power)
question, not a secure-world one.

## 12. The payload channel that works: the kernel field itself

Everything below was measured on the device. This is the first payload path that needs neither
UFS, nor USB, nor the secure world.

### How it works

```
kernel field = [ BootShim ][ UEFI FD 0x300000 ][ payload ... ]
                              ^ copied to 0x9FC00000        ^ left in place

ABL loads the whole field at  0xC0080000  (= 0xC0000000 + ARM64 text_offset 0x80000)
BootShim records {magic 'SHIM', payload address, payload size} at 0x9BA00000
the firmware reads that record and gets the payload address directly
```

Verified on hardware: the firmware printed `handoff addr=0xc03800f0 size=8388608 head='PD1936PAYLOAD-v1' MATCH`.

### Two facts about the ABL that this settled

1. **The kernel field is not limited to ~3 MiB.** That earlier conclusion came from images that
   appended the DTB directly after the kernel while declaring a ramdisk, i.e. from a layout bug.
   The retail boot image alone carries a 44 MB kernel.
2. **ABL honours the ARM64 header's `image_size`.** With `image_size = 0x3000C0` (shim + FD) the
   payload was never loaded - the firmware read three candidate bases and found nothing. With
   `image_size` covering the payload, the same image works. This field must be kept in sync with
   the real payload length; the BootShim build takes it as `PAYLOAD_SIZE`.

### Measured capacity (ascending, retail flashed before each attempt)

| payload | image | result |
|---|---|---|
8 MiB | 11.7 MiB | boots |
28 MiB | 31.7 MiB | boots |
36 MiB | 39.7 MiB | boots |
44 MiB | 47.7 MiB | refused (straight to fastboot) |

So the usable budget is **~36 MiB**, with the exact ceiling somewhere between 36 and 44 MiB.
Two further MiB are free: the FD is 3 MiB but its compressed volume only uses 693 KB, so
`FD_SIZE` can drop to 1 MiB.

### Test protocol (this cost an hour of false negatives)

Every attempt must be preceded by flashing the **retail** boot image. A failed boot leaves
`bootonce-bootloader` in `misc`, and from then on the ABL jumps straight to fastboot without even
showing the warning page - which looks exactly like "this image is broken" but is not.

### Firmware side

`MemDiskDxe` reads the handoff record and publishes `EFI_BLOCK_IO_PROTOCOL` over the payload
memory, so the existing `PartitionDxe` + `Fat` stack mounts it and `DarwinBoot` can open
`\EFI\UniXNU\Payloads\kernel.macho` with no changes.

### Payload budget versus the real payload

`payload.img` from CI is 78.6 MiB because `kernel.macho` is a DEBUG build with full DWARF. A
`llvm-strip` step was added to `kernel.yml`; the stripped kernel must come in under ~30 MiB for
the FAT payload to fit the 36 MiB channel.

### Traps worth remembering

- Assembly that references a macro the build does not define silently becomes 0: `ldr x11,
  =HANDOFF` turned into a store to address 0 and hung the device at the first screen. Always pass
  every constant used by the shim through `-D`.
- Do not write the handoff record inside the FD window: the FV occupies the full 3 MiB, and
  overwriting its tail corrupts PrePi.
- The read of `0x85CF0000` ("Boot Info") hangs - that region is not mapped in our page tables.

## 13. First XNU boot on hardware

The payload channel delivered `payload.img`, `DarwinBoot` loaded `kernel.macho`, and the kernel
reached EL1 and began kext initialisation. Screen output from the device:

```
entry words 140006F5 00000000 00000000 00000000
CurrentEL 1 SCTLR_EL1 0xC0180D TCR_EL1 0x280803510
ID_AA64MMFR0_EL1 0x101122 (PHRange 2, 4 KiB granule supported)
ID_AA64PFR0_EL1 0x11112222

Exiting boot services. A green bar across the top
marks the loader handoff before the kernel branch.
SecurityLock::LockType: SOFTWARE_LOCK, Module: 42857F0A-13F2-4B21-8A23-53D3F714B840, Function: LockCapsuleInterface, Output: Lock Capsule Interface
```

Reading of that output:

- `CurrentEL 1`, `SCTLR_EL1 0xC0180D` - the kernel is running at EL1 with its MMU configured.
- `ID_AA64MMFR0_EL1 ... 4 KiB granule supported` - the page-granule choice the port expects.
- `SecurityLock::LockType: SOFTWARE_LOCK ... LockCapsuleInterface` - an actual XNU kext
  (`SecurityLock`) is initialising, i.e. IOKit has started matching and starting drivers.
- The green band across the top is drawn by the loader itself ("A green bar across the top marks
  the loader handoff"), so it is not a display fault. Console text renders below it, which also
  proves the GOP handoff to `GopFramebuffer` works.

So the whole chain below is verified end to end on hardware:

```
ABL loads the kernel field at 0xC0080000
BootShim records the payload at 0x9BA00000 and copies the FD to 0x9FC00000
Lz4DiskDxe decompresses 12,248,931 B -> 78,643,200 B at 0x80000000 (10 blocks)
BlockIo published (153,600 sectors), PartitionDxe + Fat mount it
DarwinBoot opens \EFI\UniXNU\Payloads\kernel.macho and jumps
XNU runs, sets up EL1/MMU, starts kexts
```

### Where it stops, and why that is expected

The payload carries a kernel, not a system. There is no root volume: UFS DMA is fenced (see §10)
and no RAM disk path exists on this loader, so once the kernel finishes early kext bring-up it has
nothing to mount. Reaching `SecurityLock` is therefore the expected ceiling for a kernel-only
payload, not a regression.

### Next levers, in order of cost

1. **More log.** The console shows a fixed window; the interesting part after `SecurityLock` is
   not visible. `QcomXnuUsbDebug` would give a full console over the phone's device port (the PC
   supplies VBUS, so the host-role VBUS problem does not apply), but this UniXNU revision has no
   such component - it appears in `devices.toml` for other boards only.
2. **Root volume.** Either fix UFS DMA (blocked), or put a system image somewhere the loader can
   read. The kernel-field channel is capped at ~36 MiB, so a full rootfs cannot ride there.
3. **Stay kernel-only.** Use the boot as a driver-bring-up vehicle: each iteration adds one
   component (display, touch, USB) and verifies it from the on-screen log.

## 14. Where XNU stops, and the tools that proved it

### Established boundaries (hardware, 2026-11-19)

| Observation | Boundary it proves |
|---|---|
| blue band (probe stage 1, drawn with the MMU off) | the CPU executed past the kernel entry instruction |
| magenta band (probe stage 2) | page tables built, entering the MMU enable |
| `SecurityLock::LockType ... LockCapsuleInterface` | IOKit is matching and starting kexts |
| probe stage 3 resets exactly 5 s after the MMU is on | the probe's timer works, so it can act as a checkpoint |
| probe stage 4 after `_bsd_init` (1 s delay) never fires | `bsd_init` is **not** reached |

So the kernel dies inside IOKit initialisation, between the kext matching that starts `SecurityLock`
and the call to `bsd_init()` in `kernel_bootstrap_thread`.

### The measurement that was wrong at first

The first bisect used a 20 s probe delay while the machine dies by itself after 6-7 s, so the probe
could never have fired and the run proved nothing. A probe delay must be **shorter** than the
natural death time; 1 s is what produced the usable answer above.

### Bisect inputs

`scripts/callers.py` maps every `bl` in `__TEXT_EXEC` to its target symbol and names the containing
function, which is exactly what the probe needs:

```
_bsd_init          <- call at 0xfffffff00798dad0 inside _kernel_bootstrap_thread
_pthread_init      <- call at 0xfffffff006b04c8 inside _bsd_init
_PE_init_platform  <- calls inside _arm_init (x2) and _arm_init_cpu
_machine_startup   <- call at 0xfffffff0079b7010 inside _arm_init
```

### Colour bars cover the log

The bands are painted from row 0 at 1/16 screen height each (~146 px, 2-3 text lines on this
panel). A kernel that prints only a few lines looks silent because the bands sit on top of them.
Removing the probe's two branch words (file offsets `0x3ec488` and `0x3ee350`) keeps the panic
screen working while letting the text through.

### Panic screen: installed, but silent

`scripts/patch-xnu-entry-probe.py --panic-screen --no-reset` patches `_panic` and
`_panic_trap_to_debugger` (file offsets `0x97dac8` and `0x271520`). Nothing appeared, so the death
is not routed through either hook - consistent with a hang followed by a reset rather than a panic.

Padding is tight: the panic screen (0xa2f bytes) and the stage-3 cave cannot coexist - the patcher
refuses with "panic screen is 0xa2f bytes at ... the padding ends at ...".

### Fast local iteration

The kernel and its arguments live inside `payload.img`, so experiments no longer need a 40-minute CI
run:

```
fat_tool.py list|get|put            read and replace files in the FAT32 payload
patch_args.py --set/--drop          rewrite the XNU command line in EFI/UniXNU/unixnu.toml
patch_menu_timeout.py               change the menu timeout
panic_only.py / probe_stage3.py     install the panic screen or a timed reset, bars removed
make_payload_boot.py                shim + FD + LZ4(payload) + DTB -> boot image
```

A full cycle - patch, LZ4, package, flash - is about two minutes.

### Reset timings recorded

| Situation | Time to reset |
|---|---|
| kernel runs, no probe | ~6-7 s after the last kernel line |
| firmware retained in the menu (no kernel.macho in the payload) | ~73 s after returning to the menu |

Two different timers, so at least one reset source is independent of the kernel. The firmware-side
one is the next thing to identify.
