# Session record — 2026-11-17

Everything below was measured on the device or parsed from its own firmware. Nothing here is
"should work"; each line has an observation behind it.

## 1. What still works

| Layer | State |
|---|---|
Boot chain | BootShim + 3 MiB UEFI FD + appended DTB boots to the UniXNU menu, every time |
FrameBuffer console | primary debugging tool; `DEBUG_ERROR` reaches the panel |
XNU build (CI) | `kernel.macho` 51.9 MB and `payload.img` 78.6 MB build green on a macOS runner |

Growing the FD to 4 MiB is **not** possible: it collides with our own `SEC Heap` at
`0x9FF00000` (`ValidateMemoryMap` reports the overlap and halts). The compressed FV still has
~2.4 MB of headroom, so driver additions fit inside 3 MiB as long as the *uncompressed* content
stays reasonable.

## 2. Storage: closed, and why

The controller is healthy — this is the part that took the longest to establish:

```
UIC_CMD_DME_GET completes on the first poll (after a working W1C clear of IS)
GCC 0x77010/14/18/1c/58/5c/90/ac/c0/8c000 all report bit31 = 0 (not gated), core_clk = 0x4221
UFS_PHY_BCR = 0 (not in reset), GDSCR low byte 0 (not collapsed)
live device tree: ufshc@1d84000 has NO iommus property -> not behind apps-smmu
```

The single failing step is the controller fetching a descriptor:

```
door bell with the transfer list STOPPED -> harmless
door bell with the list STARTED         -> hangs the device
```

Six buffer placements and UFSHCI 3.0 descriptor semantics (inline UTRD, word-based offsets, per
QEMU's model) made no difference. `QCOM_SCM_MP_RESTORE_SEC_CFG` is implemented in the TZ
(`IS_CALL_AVAIL` returns 1) yet refuses every device id 1..20 with `-2`.

**Vendor binaries are not a shortcut.** `Project-Aloha/UEFIFirmwareBackup/iqoo-pd1936` holds this
exact device's signed driver set (`UFSDxe.efi` 118 KB, plus the vendor's own `APRIORI.inc` and
`DXE.inc`). The real DEPEX for all 76 drivers was recovered from the FV inside `xbl.elf`
(`tools/fv_depex_dump.py`, output in `vendor/iqoo-pd1936/vendor-depex.txt`). With those DEPEX
expressions in place `UFSDxe` still binds nothing, and the infrastructure drivers
(`ScmDxeLA` first) hang: they are XBL userspace binaries that assume XBL's SMEM / shm-bridge /
TZ runtime.

Conclusion: the UFS master's access to HLOS memory is fenced by platform protection configured
before hand-off. A plain MMIO `READ(10)` needs no secure world; making its DMA legal does.

## 3. USB host: the controller works, VBUS does not

The argument that carried this: Android moves adb/MTP traffic through dwc3 every day, so its DMA
into HLOS memory is permitted. Measured:

```
GCTL[13:12] forced to 1 (host), read back capdir = 1
XHCI CAP = 0x01100020 -> caplen 0x20, HCIVERSION 0x0110 (XHCI 1.1)
PORTSC1: PP=1, PLS=5 (RxDetect)   <- a host port actively scanning for a device
XhciDxe, UsbBusDxe, UsbMassStorageDxe all bind
```

`CCS` stays 0 and disks stay dark: **VBUS is missing**. The device tree puts VBUS on SPMI
(`pm8150_gpios 9` = `usb2_vbus_boost`, and the PM8150B SMB5 charger's OTG output).

SPMI from the firmware:

```
read : works   (arbiter v5; APID map entry holds the PPID at bits[19:8];
                obsrvr + 0x10000*ee + 0x80*apid; cmd = (opc<<27)|((addr&0xFF)<<4)|bc)
write: dropped for every APID mapped to the GPIO9 page, every write opcode
```

That is the `apid_data[apid].write_ee != our ee` rule Linux enforces. **Software VBUS is closed**
by the same class of protection as UFS. An externally powered hub is the only way to finish the
USB test.

## 4. SCM surface: wide, but gated

`IS_CALL_AVAIL` sweep: **120 calls available**. Memory-protection service `0x0C` exposes 18,
including `RESTORE_SEC_CFG` (0x02), `MP_ASSIGN` (0x16), `CP_SMMU_APERTURE_ID` (0x1B) and the
shm-bridge trio (0x1C/0x1D/0x1E). `SVC_SMMU_PROGRAM` (0x15) exposes 0x02 and 0x03 — a
CAF-private service that sounds exactly like the right lever.

Zero-argument probes:

```
MP 0x03 IOMMU_SECURE_PTBL_SIZE   -> x0 = 0 (accepted), x1 = 0 (nothing to report)
MP 0x1B CP_SMMU_APERTURE_ID      -> -5
MP 0x16 MP_ASSIGN (1 arg)        -> -5
SMMU_PROGRAM 0x02 (1 arg)        -> +4   <- only call that answered with a positive value
SMMU_PROGRAM 0x03                -> -5
same calls with 2 args           -> -5
```

A 12-vector sweep of `SMMU_PROGRAM 0x02` (arg counts 0..6, SID candidates 0 and 0x300) is built as
`boot-smmuprog.img` and still needs to be run.  Until it produces a `x0 = 0`, the "legal SCM"
route has not produced a usable entry point.

## 8. SCM: surfaced mapped, verdict reached (2026-11-18)

The full `IS_CALL_AVAIL` survey returned **120 available calls**. The memory-protection service
`0x0C` alone exposes 18, and `SVC_SMMU_PROGRAM` (`0x15`) exposes two. That surface was then
attacked with argument sweeps:

```
SVC 0x15 cmd 0x02 (SMMU_PROGRAM): 12 vectors, arg counts 0..6, SID candidates 0 / 0x300
                                  -> no vector returned x0 = 0
SVC 0x0C cmd 0x1B (CP_SMMU_APERTURE_ID), 0x16 (MP_ASSIGN), 0x0E, 0x0F, 0x23
                                  -> all rejected
SVC 0x0C cmd 0x03 (IOMMU_SECURE_PTBL_SIZE) -> x0 = 0, i.e. accepted, but it is a query
                                  ("how large must the secure page tables be"), it grants nothing
```

**Verdict: the legal SCM surface contains no call that lifts the memory fence.** The TZ routes
these commands but keeps execution authority; the one call it answers is read-only sizing
information.

### Lesson worth keeping: never hand-write `smc` in a DEBUG-heavy driver

An earlier build issued `smc #0` from inline asm and asserted immediately afterwards:

```
ASSERT [ScmTryDx] DebugLib.c(110): Format != ((void *) 0)
```

The TZ return path leaves registers in a state the asm had not declared, so the next `DEBUG`
call received a null format pointer. Any SMC from firmware must go through MdePkg's
`ArmSmcLib.ArmCallSmc()`, which saves and restores the full register set.

## 9. Where this leaves the port

| Channel | Verdict |
|---|---|
kernel field | <= ~3 MiB, already full with the FD |
boot ramdisk | this ABL requires `ramdisk_size = 0` |
DTB field | ABL ignores it (passes its own 679525-byte merged tree) |
recovery partition | never booted |
UFS from firmware | controller alive, DMA fenced; no IOMMU binding to fix; SCM refuses |
vendor UFSDxe | real DEPEX recovered, but it is XBL userspace and hangs without the XBL runtime |
**USB host** | **dwc3 accepts host role, XHCI 1.1 up, stack binds; blocked only by missing VBUS** |
software VBUS | SPMI reads work, writes are dropped by APID ownership |
legal SCM to lift the fence | none |

The single open item is external power for the USB port: with a self-powered hub the stick no
longer needs the phone's VBUS, and `CCS` changing from 0 to 1 would prove the dwc3 DMA channel -
the last physically plausible payload route on this board.
